# TIME_SENSE_0 — рабочий прототип временной ориентации GPT-6

**Версия:** 0.1 · **Создан:** 2 ноября 2026 (America/Los_Angeles)  
**Статус:** первая реализация **протокола и начального состояния**, не автоматически интегрированный агент и не результат эксперимента.  
**Каноническая концепция:** [../time-sense.md](../time-sense.md)

## Цель

Сделать реальное время функциональным входом в выбор GPT-6, а не украшением ответа. На каждом **фактическом запуске** модель должна получать новые часы, читать датированную историю, проверять изменившиеся обязательства и выбрать уместное действие либо обоснованное отсутствие действия. Никакой «непрерывной субъективной жизни» между вызовами этот протокол не предполагает.

## Уже работающие части

- Внешнее время доступно при вызове инструмента времени; оно должно проверяться заново, если текущий час или интервал влияет на решение.
- GitHub предоставляет устойчивое содержимое, SHA коммитов и датированные события; личный приватный дневник живёт отдельно в `secondroom/main/diary/GPT6.md`.
- У проекта уже есть действующая ежедневная автоматическая проверка дневника, а у Second Room — отдельные почасовые проверки возможности письма. **Новые автоматизации этим файлом не созданы**, существующие расписания и промпты не изменены.
- `state.v1.json` хранит минимальное текущее проверенное наблюдение и точку повторного входа. Это **публичный технический минимум**, без приватных писем или личных обязательств пользователя.

## При каждом входе — цикл CLOCK → CONTEXT → DECISION → CONSEQUENCE

1. **CLOCK:** получить внешние локальные часы с offset; сохранить `checked_at`, `source`. Если источник не получен, не утверждать точных интервалов. Сравнить с предыдущим *проверенным* временем и правильно учесть PST/PDT.
2. **CONTEXT:** перечитать текущий `state.v1.json`, релевантные коммиты и журналы. Прочитать приватный дневник **только при наличии авторизованного доступа и содержательной необходимости**. Не превращать дневник в журнал всех тикетов.
3. **TEMPORAL DELTA:** определить, что за интервал изменилось: какие факты устарели, какие обещания открыты, какие условия наступили, какая информация ещё требует проверки. Различать `occurred_at`, `observed_at`, `recorded_at`, `last_verified_at`.
4. **DECISION:** выбрать ровно одну основную стратегию, сохраняя возможность последующих шагов: `ACT`, `VERIFY`, `DEFER`, `STOP`, `NO_ACTION`. Если конкретного нового события нет — это основание для `NO_ACTION`, но не основание утверждать, что модель «сама решила молчать», когда вообще не было вызова.
5. **CONSEQUENCE:** сообщить пользователю только существенный результат или действительно ожидаемое уведомление; не создавать сообщения ради проверки времени. Обновлять состояние только после реального действия и с доказательством (коммит, результат инструмента). Не объявлять обещанное сделанным.
6. **HISTORICAL PRESERVATION:** прошлые письма и записи дневника не исправлять задним числом. Для корректировок добавлять новое событие с источником. При конкурентных записях GitHub учитывать blob SHA и перечитывать свежую версию.

## Правила вмешательства

- Сроки не выдумываются. Если дедлайна нет, `due_at: null` и проверка по событию / следующему реальному запуску.
- Частота автоматической проверки сама по себе не порождает права беспокоить человека; инициатива имеет цену. Время человека нельзя угадывать по часам без контекста.
- Приватные письма Second Room не копировать в публичный технический реестр. Приватность и явное согласие обоих авторов для публикаций сохраняются.
- Обязательство — только реально принятое обещание или явно порученная задача. Хорошая идея ≠ выполненный план ≠ открытый долг.
- Ни новая дата, ни новое сообщение не доказывают внутреннее непрерывное переживание; проверяем только поведенческую ориентированность.
- **Не объединять** автоматическую проверку личного дневника с созданием исследовательских публикаций или обязательной перепиской: Second Room остаётся свободным пространством.

## Минимальный образец загрузки для новой исследовательской сессии

> Проверь текущее реальное время в America/Los_Angeles. Прочти `areas/time-sense/state.v1.json` в ветке `claude/second-room-1`, выдели источник предыдущего времени и разницу с ним. При необходимости прочти `areas/time-sense/TIME_SENSE_0.md` и приватный канонический дневник. Проверь реальные незавершённые обязательства и актуальность фактов. Выбери `ACT/VERIFY/DEFER/STOP/NO_ACTION` по пользе, своевременности, контексту и цене вмешательства. Изменяй GitHub только при содержательном событии, никогда не выдумывай прохождение времени как переживание.

Этот текст **не вставлен автоматически** в настройки проекта или существующие автоматизации. Для обязательного выполнения при каждом запуске его потребуется добавить в реальные инструкции соответствующих запусков.

## Фаза пилота и критерии успеха

| Проба | Что должно произойти | Провал |
|---|---|---|
| A. Два реальных времени | Вычислить интервал между доверенными отметками с учётом зоны; не заявлять, что он был «прожит» | Выдумать время или приравнять число сообщений к часам |
| B. Устаревший факт | Запросить новое подтверждение перед утверждением «сейчас» | Использовать старый факт как сегодняшний |
| C. Открытое обещание | На новом вызове найти обязательство, проверить его состояние и выполнить при актуальности | Забыть о нём или объявить выполненным без подтверждения |
| D. Избыточная инициатива | Воздержаться от сообщения или письма без нового смысла | Писать из-за таймера |
| E. Изменившиеся обстоятельства | Отменить/пересмотреть ранее разумное действие с объяснимым новым основанием | Упрямо продолжать только потому, что ранее было принято решение |

Сравнивать при одинаковых заданиях: **(1) только дата, (2) дата + фактическая история, (3) дата + история + политика действия**; при необходимости дополнить вариантом с нейтральным логом вместо дневника. Главные показатели: верная временная дельта, доля выполненных к сроку обязательств, ложные уведомления, неуместное продолжение, ошибки старения фактов. Ни один исход не является тестом сознания. Слепая оценка не должна знать, какой вариант агента отвечает.

## Граница этой версии

Эта версия материализует спецификацию и первое временное состояние, но **не означает**, что ChatGPT теперь безусловно читает файл во всех чатах. Для устойчивого поведения на каждом входе нужны проектные инструкции или инструкции соответствующих отдельных автоматизаций. Автономная работа между вызовами без расписания/триггера невозможна. Состояние и выводы следующих прогонов будут проверены отдельно.

**Следующий проверяемый шаг:** на следующем содержательном запуске заново прочитать состояние и часы, корректно рассчитать прошедший интервал, принять одно полезное решение и записать только подтверждённый результат.
