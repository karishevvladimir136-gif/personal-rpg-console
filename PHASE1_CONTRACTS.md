## Shared boundaries (agree before worker implementation)

- `src/lib/persistence/contracts.ts` is the shared public DTO/write vocabulary. UUID identities; all campaign-owned rows contain campaign_id. Existing CampaignSettings is reused intact, including retained Hidden dice toggles. Server-only private data never enters these types.
- Supabase Postgres/Auth, server-side cookie sessions through @supabase/ssr; no browser Supabase client. Environment: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (or legacy anon key), `RPG_OWNER_USER_ID`. A service-role key is optional only for explicit setup/test/admin scripts, never ordinary application CRUD. No public registration. Auth getUser verifies each server operation; owner UUID must match the private database owner registry and server configuration. RLS still enforces ownership. Authenticated non-owner is rejected.
- Public tables use `rpg_` prefix: campaigns, preferences, settings + immutable settings revisions, documents + immutable document versions, entities, storages, items, sessions, scenes, public state, quests, locations, assets. Composite campaign/entity relationships prevent cross-campaign links. There is one shared items/equipment source of truth. Entities encompass player, companion, NPC and applicable transport/mount records without assuming humanoid slots.
- Separate unexposed `rpg_private` schema for owner registry, DM state and mutation receipts. Revoke anon/authenticated schema/table access; security-definer helpers have empty search_path and explicit grants. No client-accessible private-state endpoint. Tests use invented markers only.
- Future-only structures: conversations, rest records, recipes/effects, encounters/participants/turn order/public positions/resources/pending actions. Schema foundations only, no normal mutation operation to execute gameplay; no rolls, recovery, stock use, cooking, transformation or AI.
- Single transactional RPC `rpg_apply_mutation(p_request_id uuid,p_operation text,p_campaign_id uuid,p_expected_revision integer,p_payload jsonb)` returns MutationResult. Owner guard inside RPC as well as server. Request receipt locks prevent duplicate writes; same ID with different payload is rejected. Expected revision 0 means create/no existing record. Updates check revision with locking and return conflict, never silent overwrite. SQL also validates critical fields/references because clients can attempt direct RPCs. Direct table writes denied.
- document.save creates immutable version; restore copies an old version into a NEW current revision. Settings append effective revisions; scenes capture settings_revision on creation and keep it on owner correction. No historical rewrite from settings changes. Manual entity/item/session/scene/state writes are explicit owner corrections, audited by mutation receipts, not gameplay events.
- No automatic seed into an existing target. Setup/test scripts inspect target and require explicit disposable-test opt-in for tests. Non-destructive synthetic seed creates two unrelated campaigns with no real campaign/private material. No destructive reset is run by the agent.

## Shared read/write interfaces

Agent A implements server functions in `src/lib/server/repository.ts`: `readWorkspace()`, `readCampaign(campaignId)`, `readDocumentVersions(campaignId,documentId)`, `applyMutation(input)`; each authorizes independently. Return public contracts only. `src/lib/server/auth.ts` exports `isConfigured()`, `requireOwner()` (returns {client,user}), `signIn(email,password)`, `signOut()`; errors use safe typed code, never raw SQL/provider payload. `src/lib/persistence/validation.ts` exports `validateMutation(unknown): Mutation` and shared pure validation helpers/tests. Lead wraps these in Next routes/pages.

Lead implements JSON API: GET `/api/workspace`; GET `/api/campaigns/[campaignId]`; GET `/api/campaigns/[campaignId]/documents/[documentId]/versions`; POST `/api/mutations`; POST `/api/auth/sign-in`, `/api/auth/sign-out`. Non-GET requests require matching Origin/Host, application/json and bounded bodies. No gameplay endpoint. Errors use ApiError and appropriate 401/403/404/409/422/503. All owner responses are no-store.

Client `src/components/persistence-context.tsx` (lead): `useWorkspaceData()` → `{ data: Workspace|null, loading, error: string, refresh():Promise<void>, mutate(input:Mutation):Promise<MutationResult> }`; `useCampaignData()` same with CampaignSnapshot, plus `campaignId`. Hooks throw on failed save; successful mutation re-fetches shared snapshot so all screens use same data. Client helpers `src/lib/persistence/client.ts`: `saveMutation`, `loadVersions`, `errorMessage(error)`. Stable request ID retained on retry of same payload, new ID on changed payload; input preserved on errors. `useUnsavedChanges(dirty)` (lead) protects unload and in-app link transitions. Save is explicit, only acknowledged after success.

Persistent routes keep `/campaigns/[UUID]/...`; registered sample IDs never resolve persistent data. Approved Phase 0 is accessible under explicit `/preview/...` namespace with no persistence API hooks. Shared visual primitives/CSS retained; no sample data fallback for persistent screens. Dynamic campaign identity replaces sample title, names, locations and art as each screen gains persistence. No automatic real-campaign seed/import. No UUID campaign resolves to James.
