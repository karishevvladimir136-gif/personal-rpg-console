## Storage decision and immutable identity

Phase 3 has campaign-global current rows, global unique record IDs, immutable source history and campaign-wide memory flags. Adding a timeline predicate only to search would leak future state, aliases, knowledge and pinned turns. Rather than rewriting every table into a second gameplay system, retain existing tables as the single **active campaign projection** and add private immutable row-version storage plus save/head manifests.

Timeline UUID belongs to a campaign. A root timeline is backfilled without changing gameplay. A fork has parent timeline UUID, immutable fork save UUID and inherited source boundaries. A campaign has exactly one active timeline and a monotonic activation epoch. Public `TimelineFence = { timelineId, epoch }`; epoch increments on activation and is never restored backwards. Runtime revision also remains monotonic across activation. Save UUID identifies an immutable manifest and public metadata, never a prose recap. Timeline head pointers and the one current Quick Save pointer are mutable; referenced saves/versions are immutable.

The private row-version vault deduplicates canonical row payloads by campaign, allow-listed table, stable row key and content identity. A manifest references versions; repeated saves do not copy the transcript or the database. Original active rows must be archived and verified before replacement. Vault and save payloads reject update/delete unconditionally. Never prune versions referenced by a save, head or ancestor. Media bytes are not copied.

An immutable save records exact projected record-version membership, public/private source watermarks, original runtime/state revisions, effective settings/guide revisions, memory generation and source references. A child initially inherits exactly its fork save's membership. Its new writes extend or replace only its active row-version membership. A parent's later versions/events cannot enter that child. Multiple forks inherit ancestor history only through successive manifests, never by unrestricted access to parent rows. This is the ancestry rule, including corrections and knowledge, not a timestamp heuristic.

## Exact capture and activation

Capture branch-owned public entities/storages/items, sessions/scenes/public state, quests/locations, conversations, rests/recipes/effects, encounters/participants/pending actions, session guidance and provenance; runtime state/configuration, non-feedback turns/checkpoints/commands/events and DM state; both memory source paths, aliases/restrictions, boundaries/checkpoints/summaries/jobs and coverage/generation. Capture effective settings and the guide's current document pointer/value. Include relationships/conditions/equipment and embedded-component provenance wherever represented in these existing records.

Campaign identity, application preferences, ordinary campaign-wide canon/reference documents, immutable document/settings version histories, feedback messages and feedback runtime evidence, assets and global correction generation remain outside historical rollback. Feedback does not become world history. Effective guide/settings restore from the save while their original immutable versions remain available. Future saves allocate new document/settings version numbers above the global maximum, never overwrite a sibling version. Foreign keys from retained feedback/history use stable identity registries when their referenced active session/turn is absent. Current gameplay still requires active records; an identity registry does not grant runtime visibility.

Activation takes the existing campaign lock before runtime/timeline locks. It validates owner/campaign, exact fence, runtime/catalog revisions and all manifest references before any replacement. Capture the old head and a clearly labeled safety-before-load save in the same transaction, then create a child for Load or activate a preserved existing head for Switch. Failed validation/restore rolls everything back, including safety/new-branch creation. The old timeline's gameplay head remains exact; technical leases may be revoked safely. Load never erases the old future or replays its mutations.

Rematerialize only the fixed campaign projection from validated manifest refs. A private transaction-scoped restore-guard table, inaccessible to callers, permits projection replacement and suppresses re-index/revision triggers during restoration. Do not use a caller-settable flag as authority. Existing immutable active-projection rows can be replaced only after exact payload archival; immutable originals live in the vault. Defer appropriate FKs for the atomic replacement, use `OVERRIDING SYSTEM VALUE` for saved identity sequences, omit generated search columns, and never reset sequences. Normal readers cannot observe an intermediate working set.

After restoration, advance the monotonic runtime revision/epoch, rebind technical revision/fence fields of pending execution and valid memory projections, and revoke all old turn/job lease tokens. This rebinding changes no input text, plan, outcome, dice, effective rules, resource value or narration. If required provenance is absent or invalid, fail safely; never manufacture a resume state. An inherited valid summary/checkpoint remains valid only when every source ref belongs to the restored manifest and campaign-global canon/restriction rules still permit it.

## Pending turns, dice and idempotency

Save captures the durable accepted point without resolving anything. Quick/manual save may refuse with a neutral busy error if a currently leased operation cannot be captured coherently; otherwise record pending input, plan/checkpoint, exact check IDs/results and confirmation status. Loading revokes old execution leases. An unresolved inherited operation resumes its original recorded checks; no RNG merely on refresh/retry/activation. A genuinely new future operation has a fresh operation ID on the new timeline and may roll once normally.

All campaign writes carry the original browser timeline fence, never silently replace it with the current server fence. Same request ID/content returns the previous safe result without another save/fork/safety point; changing content/fence under that ID conflicts. Global load/switch command receipts survive switching and bind owner/campaign/action/body; replay returns current safe status and the original affected save/timeline IDs, never reactivate an old result silently. Timeline-scoped gameplay/memory command receipts cannot be used to mutate another active timeline. An inactive operation cannot be resumed there merely because its UUID is known.

Record revisions alone cannot prevent ABA after restoring old values. Fence validation is required in database wrappers, including direct owner RPC calls, pending turn resume/cancel/reroll, guide approvals and manual corrections. For existing legacy regression callers, missing fences may be accepted only on the original never-activated root at epoch 1; after any activation, missing/stale fences conflict. New UI/API requests carry fences. Private runtime stores bind one fence for the whole request, including after-response jobs; never automatically claim a newly activated timeline from an old callback.

Autosave policy is campaign-level and not rolled back: `autosave: off | session | turn`, default `session`; retention integer 10–20, default 15; `loadMode: unrestricted | checkpoints | restricted`, default `unrestricted`.
