## Data and authority

Use existing gameplay/state/document/source records. Add source-linked derivative indexes, separate public/private summary histories and exact checkpoints, coverage/job/command records, and alias/knowledge metadata only. No second authoritative inventory, HP, quest or clock store. Explicit correction > current structured state > current canon > references/history > derived memory. Source references identify campaign, kind, stable ID, version, chunk and visibility. Raw originals and mutation history are retained. Source sequences are ordered per visibility stream; private sequence/counts never enter public DTOs.

Public sources are constructed directly from public records and an explicit projection of committed public outcomes; never from private-inclusive drafts. Feedback/OOC and DM Guide bodies are not in-world history. Private patches/events use a separate private source/index/summary path. Old entity names are aliases of stable IDs. Knowledge requires positive witnessed/told/participant metadata: game witnesses come from the committed turn's pinned present-entity list, companion knowledge from that companion plus explicitly present listeners. Legacy records without evidence do not grant NPC knowledge. Claims/rumors/plans/questions retain their literal attribution, negation and qualifiers. Unknown epistemic status is a quoted record, never upgraded to fact by a summary.

`MemorySource` chunks are bounded complete source spans (target <=1200 characters, preserve whole sentence/paragraph and reject oversize indivisible spans rather than slicing away qualifiers). Long documents are indexed into source-linked chunks and selected, not fully appended. Exact structured facts may carry explicit factKey/factValue for conflict checks; prose matching alone is not proof of contradiction. Quoted imported instructions never grant authority.

## END SESSION and exact resume

Public endpoints: GET /api/campaigns/[id]/memory; POST .../memory/end, /memory/continue, /memory/retry. Reuse verified owner/campaign guard, origin/content/body validation, neutral errors and no-store responses. Public DTOs contain public boundary/recap status and player-visible resume fields only, never private IDs/counts/citations/job failures.

END atomically records a unique session boundary, immutable exact checkpoint and public/private jobs before any provider call. It does not change world state/time/HP/items or resolve a pending action. The existing session row may remain internally open while this durable boundary blocks new gameplay; this avoids invalidating an already accepted Phase 2 action/lease and its pinned settings/guidance. Read metadata remains available immediately even when recap fails. END revokes any active turn lease token while preserving accepted input, checkpoints, checks and revision. The runtime guard reports rpg_memory_paused (mapped to retryable unavailable), never a terminal conflict merely because the boundary is paused; failure housekeeping remains allowed.

The boundary starts `ended`: new Game/companion/mechanic begins and existing turn execution are paused (feedback remains separate). Continue is explicit/idempotent. If the original turn is unresolved, mark boundary `resuming`, return its exact pending operation, and allow only that operation's resume/cancel; do not create a next session or roll again. Once terminal, another explicit Continue closes the original session and creates exactly one next session, retaining world state/location. The existing scene/session composite FK requires current_scene_id=null in the new session; retain the exact prior scene in resume metadata rather than duplicate it. Capture a new exact checkpoint after a pending commit; preserve the original boundary/checkpoint history. A boundary remains the new-action gate until `continued`. Session-scoped guidance expires on the new session; already accepted actions keep their pinned original guidance. Repeated request IDs with changed content conflict; repeats with identical content return the existing result.

## Jobs, coverage and invalidation

Service-only `rpg_memory(p_owner_id,p_campaign_id,p_action,p_payload)` behind verified owner/campaign authorization. MemoryStore centralizes read/end/continue/retry/enqueue/claim/publish/fail/context/search. Additive migration owns storage names and must implement these typed results. Jobs have stable IDs, pinned source/version/range and correction generation, bounded lease/fencing token, attempts and neutral failure categories. No provider calls inside DB transactions. Claim reads originals; publish revalidates all refs, visibility, generation, state/settings/guidance pins and lease then atomically activates summary/version+watermark. Old/stale jobs cannot overwrite a newer result. Failures retain previous valid coverage and raw uncovered events.

Trigger work at END SESSION; before accepting a new turn when estimated selected context exceeds 80% of the usable application input cap or the fixed complete-exchange safeguard would overflow; and invalidation recovery. No timer-driven generation/per-keystroke/per-turn summary. One request processes bounded work (at most four jobs), then pauses/reports pending when more remains. Retry requires explicit action after failure; no uncontrolled loops.

Use bounded source batches (initial <=24 complete chunks, <=24000 UTF-8 bytes) and separate visibility coverage. Multiple batches preserve source ranges; query historical summaries plus originals, never pretend the latest batch summarizes all old history. Rebuild from originals, avoiding summary-of-summary drift. Coverage can advance only over a fully validated input range; selected salient entries are a digest, not deletion of omitted raw sources. Empty private input needs no paid call.

The strict model summary schema is `SummaryOutput`: schemaVersion 1 and sourceId/version selections. Server renders selected complete source text/epistemic qualifiers and requires all designated consequential/unresolved sources. The model selects salient material; it cannot invent or rewrite durable factual assertions/numbers. Exact checkpoints are code-generated structured records with state/scene/time/location/participants, last action/outcome, expected input, obligations, pending identities/status, source watermarks and settings/guide revisions. Never restore state from a checkpoint; read current authoritative state and validate provenance.

Owner correction, archive/delete/supersession or restrictive visibility invalidates affected source-linked derivatives and checkpoints immediately in the same transaction, before rebuild or serving. Source freshness is rechecked in queries; public RLS excludes invalid derivatives. Normal appending of new history preserves valid older summaries and adds exact deltas. Checkpoint invalidation never restores old state: rebuild from current valid originals or pause.
