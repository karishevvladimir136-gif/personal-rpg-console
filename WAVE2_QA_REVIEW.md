## Confirmed defects

**W2-QA-01 — Pending source-derived work remained approvable after its source was replaced (high, FIXED and independently verified).** In `src/lib/world-library/authoring.ts`, `compiler.step` computed source changes but returned an existing `awaiting_review` draft before the invalidation branch. `pack.approve` did not check whether a pending compiler draft still referred to current source versions.

Reproduction: create a synthetic source and finish its four explicit compiler passes; replace that source with a new immutable version; request another compiler step using the saved job version; approve the existing draft. Observed before the correction: the step returned the old pack, the latest job remained `awaiting_review`, and approval succeeded. The Lead now creates immutable invalidated job versions when a source changes, checks current source/job history before approval, and preserves exact successful receipt replay. Application regressions and the direct SQL stale-approval regression pass. Actual SQL authoring also confirms that already-approved historical packs and campaign pins remain unchanged and that a previously successful approval operation remains replayable after source correction. The SQL trigger executes under the existing owner lock; the test exercises a stale-request interleaving, not live concurrent clients.

**W2-QA-02 — Public recovery metadata revealed private-only stage presence (medium, FIXED and independently verified).** Migration 11 originally added `worldRecovery` only if the turn's internal checkpoint contained `worldSettlement`. A console-basic action with a private-only staged Event therefore had a different public response from the same action without that private stage. Reproduction used a real one-Event private stage and compared `runtime_public_turn` on the stored turn with a nonmutating composite clone that omitted only the internal settlement. The sole response difference was `worldRecovery: "available"`. The Lead made recovery metadata generic for unfinished actions, with neutral failure copy. The independent equality regression and existing recovery privacy regression both pass after the correction.

**W2-QA-03 — SQL rejected the compiler's exact text evidence (high, Lead-discovered, FIXED and independently verified).** The Wave 1 SQL evidence validator required each evidence digest to equal its whole-source digest, while the new compiler emits a digest of the exact UTF-16-indexed source passage. All three new real-SQL authoring tests stopped at draft materialization with a validation failure before the correction. The Lead added UTF-16-aware exact-span validation and future-source classification enforcement to migration 11. The complete actual-SQL authoring flow now passes with BOM, Cyrillic, astral Unicode, and CRLF text. Wrong digests, split-surrogate boundaries, and future-source laundering fail without persisting a record. Legacy whole-source evidence remains supported. This mismatch was not detected by the pure in-memory authoring tests.

**W2-QA-04 — A World Logic checkpoint could reach legacy commit without a settlement (high, Worker C-discovered, FIXED and independently verified).** The SQL commit wrapper previously invoked the World validator only when a packet or stored stage contained a settlement. The Lead now requires an object settlement and an existing campaign/operation-scoped stage whenever the checkpoint contains World Logic. The independent regression writes a valid observe proposal with a forged HP-changing resolution, then attempts commit with an omitted, null, and empty-object settlement while no stage exists. Every attempt fails; HP, time/runtime revision, scene history, stages, Events, and the generating turn status remain unchanged. The Lead's guard was present before the first independent execution, so this reviewer verified the fix without claiming a pre-fix reproduction.

**W2-QA-05 — Mixed JSON types could bypass mandatory resolver evidence indexing (high, Worker C-discovered, FIXED and independently verified).** Distinct JSON entries such as `0` and `"0"` previously passed the receipt's distinct/count check before both were cast to integer zero, omitting the second required evidence entry. Migration 11 now checks JSON numeric integer values before casting, including the action path. The direct SQL resolver-receipt regression accepts `[0,1]` for two mandatory entries and rejects `[0,"0"]`, `["0",1]`, `[0,0]`, `[-1,1]`, and `[0,1.2]`. The fix was present before the first independent execution; the finding is credited to Worker C.
